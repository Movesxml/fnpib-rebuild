## 7. 兼容性风险

- **Swift 6 strict concurrency**（project.yml 已开）：`SharedRandomSource` 是 class 且**不标 `Sendable`**。
  随机源只能在单一执行域（逻辑帧推进所在的 actor/线程）内使用。
  现有驱动链是主线程 `CADisplayLink → tick`，符合单域约束 `[待验证]`。
  **不要**为了消编译错误加 `@unchecked Sendable` —— LCG 状态无锁，加了就等于谎报线程安全。
- **iOS 27**：`UInt32.random(in:)` 底层走 `SystemRandomNumberGenerator`（arc4random），
  自 iOS 9 起稳定可用，无 API 风险。它只用于播种，不参与游戏随机流推进。
- **回放/存档**：若将来要做确定性回放，必须能序列化 LCG 内部状态；
  当前 `OriginalLCGRandom` 是否暴露状态字段 `[待验证]`，不在本卡片范围。

//
//  SharedRandomSource.swift
//  FNPBCore
//
//  [T-042] 条件性落盘：仅当 `OriginalLCGRandom` 是值类型（struct）时需要。
//  若它本身已是 final class（引用语义），本类型无必要，Kimi 直接跳过本文件，
//  让 App 持有 OriginalLCGRandom 实例即可（效果等价、改动更小）。
//

/// 全游戏唯一随机源的持有者。
///
/// 存在理由：若 `OriginalLCGRandom` 是值类型，把它作为参数在
/// GameWorld / WaveDirector / SpawnTable 之间传递时，每处都拿到一份
/// **独立拷贝**的 LCG 状态 —— 从第一个随机消费点开始就分叉成多条互不
/// 相同的序列。这与原版「一个会话一条流」的行为不符，且不可重现。
/// 本类以引用语义持有唯一生成器，保证「一个游戏会话 = 一条随机流」。
///
/// ⚠️ 并发：刻意不标 `Sendable`。LCG 状态无同步保护，只能在单一执行域
/// （逻辑帧推进所在的 actor / 线程）内使用。跨域共享需引入锁或改为 actor，
/// 属本卡片范围外。不要为了消编译错误加 `@unchecked Sendable` —— 那是谎报线程安全。
public final class SharedRandomSource {

    /// 出厂种子。仅用于诊断与回放记录，不参与随机推进。
    public let seed: UInt32

    /// 唯一生成器实例。调用方只能读取使用，**不得**拷贝重建或另起新实例。
    public let generator: OriginalLCGRandom

    public init(seed: UInt32) {
        self.seed = seed
        self.generator = OriginalLCGRandom(seed: seed)
    }
}

//

import XCTest
@testable import FNPBCore

final class GameRandomSharingTests: XCTestCase {

    // MARK: - 1. 共享实例 = 单一序列（自证，不依赖 golden）

    /// 共享随机源在两个消费方之间必须推进**同一条**序列。
    /// 判定方式：与「两个同种子的独立实例交叉推进」对照 —— 后者会在首步就重复，
    /// 前者不会。该断言不依赖任何具体数值，因此不存在捏造基线的问题。
    func testSharedSourceAdvancesOneStreamNotTwo() {
        let seed: UInt32 = 0x5EED_1234

        let shared = SharedRandomSource(seed: seed)
        let consumerA = shared.generator
        let consumerB = shared.generator
        XCTAssertTrue(
            consumerA === consumerB,
            "两个消费方必须持有同一个生成器实例；值拷贝会在首个消费点分叉成两条序列"
        )

        let sharedSeq = [
            consumerA.nextUInt32(), consumerB.nextUInt32(),
            consumerA.nextUInt32(), consumerB.nextUInt32()
        ]

        // 对照组：两个独立实例（模拟“不小心各建一个”的 bug）
        let forkA = SharedRandomSource(seed: seed).generator
        let forkB = SharedRandomSource(seed: seed).generator
        let forkedSeq = [
            forkA.nextUInt32(), forkB.nextUInt32(),
            forkA.nextUInt32(), forkB.nextUInt32()
        ]

        // 前提校验：同种子的两个独立实例首步必然相同
        XCTAssertEqual(forkedSeq[0], forkedSeq[1], "前提校验失败：同种子独立实例首步应相同")
        // 核心断言：共享推进的是单一流，与分叉流必然不同
        XCTAssertNotEqual(
            sharedSeq, forkedSeq,
            "共享实例的序列与分叉序列相同 —— 说明装配链上仍存在两条独立随机流"
        )
    }

    // MARK: - 2. 共享层是纯转发（不得引入额外状态或第二语义）

    /// `SharedRandomSource` 只做持有，不得改变底层生成器的输出。
    /// 这保证「不新增第二随机序列」在实现层面可被机器验证。
    func testSharingLayerIsPureForwarding() {
        let seed: UInt32 = 0x0BAD_F00D
        let shared = SharedRandomSource(seed: seed)
        let raw = OriginalLCGRandom(seed: seed)

        for i in 0..<64 {
            XCTAssertEqual(
                shared.generator.nextUInt32(),
                raw.nextUInt32(),
                "第 \(i) 次取值出现分歧：共享层引入了额外状态或额外随机推进"
            )
        }
    }

    // MARK: - 3. 快照回归：同种子位精确可重放

    /// 相同种子两次构造，前 N 项必须逐位一致。
    func testSeedReplayIsBitExact() {
        let seed: UInt32 = 0x00C0_FFEE

        func run() -> [UInt32] {
            let source = SharedRandomSource(seed: seed).generator
            return (0..<32).map { _ in source.nextUInt32() }
        }

        XCTAssertEqual(run(), run(), "同种子重放不一致：随机源装配非确定性")
    }

    // MARK: - 4. 序列指纹跨运行稳定

    /// 取 256 项的 FNV-1a 指纹两次，必须一致。
    /// 用于捕获「装配层让序列随进程状态漂移」这类回归（例如误用系统随机源推进游戏流）。
    func testSequenceFingerprintIsStableAcrossRuns() {
        func fingerprint() -> UInt64 {
            let source = SharedRandomSource(seed: 0x9E37_79B9).generator
            var h: UInt64 = 0xcbf2_9ce4_8422_2325          // FNV offset basis
            for _ in 0..<256 {
                h = (h ^ UInt64(source.nextUInt32())) &* 0x0000_0100_0000_01b3  // FNV prime
            }
            return h
        }

        XCTAssertEqual(
            fingerprint(), fingerprint(),
            "序列指纹不稳定：随机流可能被外部熵源污染（应为纯 LCG 确定性推进）"
        )
    }

## Kimi 审查时应注意的风险点

1. **API 签名全部是假设**（最优先）：`OriginalLCGRandom(seed: UInt32)`、`nextUInt32()`、`RandomSource` 协议是否 `mutating`、`GameWorld.init` 参数表 —— 我都没有源码证据，均标了 `[待验证]`。若实际不符，测试文件需按名替换，`===` 断言在值类型情形下非法。

2. **`SharedRandomSource` 可能是多余抽象**：若 `OriginalLCGRandom` 已是 `final class`，直接持有实例即可，多了这一层反而是改动量。README §4 给了裁决表和判断命令，请以实际类型定夺，不要默认采纳。

3. **`===` 断言的两面性**：它精确捕获"值拷贝 fork 序列"这个本卡片的核心缺陷，但也把测试绑死在"引用类型"上。若最终走 struct 路线，测试 1 需重写为转发方法对比。

4. **`UInt32.random(in:)` 的边界**：它是种子熵源，不是游戏随机流，我判断不违反"不新增第二随机序列"。但若 Kimi 认为"装配层不应用系统随机"更严格，可改为从 `FNPBPlatform` 已有的启动时间/设备标识取熵——那会引入平台层依赖，测试目标就跑不动了，请权衡。

5. **golden 基线缺失是刻意的**：任务卡禁止捏造官方种子，同理我拒绝捏造序列常量。若验收要求必须有数值基线，需先跑 `OriginalLCGRandom` 既有 CI 拿到实测输出，不能由本 agent 生成。

6. **验证边界必须写进 PR**：App 层装配（`@main`、驱动链）不在 `FNPBCore` 测试目标内，"随机源唯一"在自动化层面只被部分保障，剩余靠 `grep` 审计（README §6）+ 人工审查 `GameWorld` 内部的随机消费点。这一条不要被"CI 通过"掩盖。

7. **`SharedRandomSource` 不标 `Sendable` 是刻意的**：Swift 6 strict concurrency 下若出现跨 actor 访问会编译失败，那是**正确**的失败。不要加 `@unchecked Sendable` 消错。

8. **不改 UI / 挑战选择 / 资源加载**：草案严格遵守；但 `GameSessionController` 这个类名是我虚构的装配根，若生产文件结构不同（如直接在 `@main struct` 里持有 `GameWorld`），H1 的落点要跟着搬，注意别把 `GameHostView` 的构造签名一起改坏。
