## 设计说明

**分层**：`ScreenID`（纯 ID 映射）→ `GameSnapshot`（纯值快照 + Intent/ViewModel 协议）→ `UISupport`（共享视觉基元 + 唯一的 UIKit 依赖点）→ 五个屏幕视图。屏幕全部是**纯值输入 + 闭包输出**的无状态 View，App 层可用 `@Observable` model 包一层即可接入 60Hz 帧驱动。

**关键取舍**
1. **不 import FNPBCore**：`GameSnapshot` 是 FNPBUI 自有值类型（`Sendable`），字段语义在文件头列出「数据来源映射」，App 层负责组装。
2. **反向通路**：`UIIntent` 枚举 + `UIActions`（普通非隔离 struct，闭包假定主线程调用）。**刻意不给 `UIActions` 加 `@MainActor`**——避免 Swift 6 下「把 MainActor 闭包塞进 Button action 的非隔离参数」这类隔离降级诊断；App 层构造点的隔离写法在 `UIActions` 文档注释里给了 `MainActor.assumeIsolated` 示例并标了 `[待验证]`。
3. **资源**：不给任何未确认的 PNG 文件名。全部走语义 key（`screen.<uiscreen>.<element>`），`UIArtwork.image` 找不到就回落色块——符合任务卡「禁止臆造资源名」。真实文件名待资产管线清单产出后回填。
4. **UIKit 收敛到单文件**：`Image(uiImage:)` 需要 `UIImage`，故 `UISupport.swift` 必须 `import UIKit`；其余屏幕文件只 `import SwiftUI`。无任何 `UIViewRepresentable`。
5. **project.yml 无需改动**（假设 `Sources/FNPBUI` 按目录收录，子目录 `Screens/` 自动包含）——`[待验证]`，见风险点。

//  锚点：IPA 解包产物 `assets_raw/xml/screens/` 下的 20 个 `.uiscreen` 文件

    }
}

//
//  UISupport.swift
//  FNPBUI — 界面层 v1（T-021）
//
//  共享视觉基元（配色 / 素材装载 / 按钮 / 屏幕骨架）。
//
//  ⚠️ 这是 FNPBUI 里**唯一 import UIKit 的文件**：
//     仅因为 `Image(uiImage:)` 需要 `UIImage` 把 assets 管线产出的 PNG 装进 SwiftUI。
//     本文件不含任何 `UIViewRepresentable`——MTKView / TouchRouter.captureView 的桥接
//     若存在，归 FNPBRender / FNPBPlatform（此处不重复实现，也不猜它们的 API）。

//  ⚠️ 素材策略（遵守任务卡「禁止臆造资源名」）：
//     不硬编码任何未经确认的 PNG 文件名。所有素材按**语义 key**（`screen.<uiscreen>.<element>`）
//     查找，查不到即色块回落并保留版面，绝不导致崩溃。
//     [待验证] key → 真实文件名的映射待 tools/AssetPipeline 产出清单后回填

/// 占位配色方案。
/// [待验证] 原版主色取自贴图（assets_png），未做取色采样；此处为可读性占位值，

    public static var ink: Color { Color(red: 0.10, green: 0.08, blue: 0.07) }
    /// 羊皮纸白（主要文字）

    /// 金色（主按钮 / 高亮）
    public static var gold: Color { Color(red: 0.98, green: 0.76, blue: 0.24) }
    /// 朱红（危险 / 生命标记）
    public static var accent: Color { Color(red: 0.86, green: 0.25, blue: 0.16) }
    /// 背景兜底色
    public static var backdrop: Color { Color(red: 0.16, green: 0.12, blue: 0.10) }

    public static var panelFill: Color { Color(red: 0.20, green: 0.15, blue: 0.12).opacity(0.95) }

    public static var placeholder: Color { Color(red: 0.30, green: 0.24, blue: 0.20) }

// MARK: - 素材装载

public enum UIArtwork {

    /// assets_png 产物在 bundle 内的子目录。
    /// [待验证] 与 pipeline / XcodeGen 的 resources 拷贝目标需对齐（当前假设为 `Assets/`，且允许平铺兜底）。
    public static var subdirectory: String { "Assets" }

    /// 按语义 key 查 png 文件路径。找不到返回 nil（调用方回落色块）。
    public static func url(for key: String, bundle: Bundle = .main) -> URL? {
        bundle.url(forResource: key, withExtension: "png", subdirectory: subdirectory)
            ?? bundle.url(forResource: key, withExtension: "png")
    }

    /// 按语义 key 装载图像。
    /// 先试 asset catalog（若资产管线最终产出 xcassets，`UIImage(named:)` 自带缓存），
    /// 再回落到 bundle 内的 assets_png 产物。
    /// [待验证] 文件回落路径无缓存，逐帧调用会重复解码；真机联调前应改为 xcassets 或加缓存。
    public static func image(_ key: String, bundle: Bundle = .main) -> UIImage? {
        if let named = UIImage(named: key, in: bundle, compatibleWith: nil) {
            return named
        }
        guard let url = url(for: key, bundle: bundle) else { return nil }
        return UIImage(contentsOfFile: url.path)
    }
}

## 需要 Kimi 审查时注意的风险点

1. **`import UIKit` 的位置偏离约束 3 的字面表述**（但符合精神）：`UISupport.swift` 必须 `import UIKit`，因为 `Image(uiImage:)` 的形参是 `UIImage`。已把 UIKit 依赖**收敛到唯一文件**，其余 5 个屏幕文件只 `import SwiftUI`，全工程无 `UIViewRepresentable`。若你要求严格零 UIKit，则只能用 `Image("name")`（需要 xcassets），那要等资产管线先出 xcassets。

2. **`UIActions` / `UIIntent` 刻意不加 `@MainActor`**（约束 1 只要求 ViewModel 协议标 `@MainActor`，已满足）。原因：加隔离标注会让 `Button { actions.send(...) }` 在 Swift 6 严格并发下产生「主线程闭包赋给非隔离函数类型」的诊断。代价是**隔离责任转移到 App 层构造点**——文档注释给了 `MainActor.assumeIsolated { model.send(intent) }` 的写法并标了 `[待验证]`，**该写法未在 Mac 上编译验证**（本机 Windows）。这是本卡最可能的编译失败点，请优先在 CI/真机校验。

3. **资源名一个都没硬编码**（严格遵守「禁止臆造资源名」）：全部走 `screen.<uiscreen>.<element>` 语义 key + 色块回落。这意味着 **v1 在真机上就是纯色块界面**，直到资产管线（tools/AssetPipeline）产出清单回填 `UIArtwork`。若你认为 v1 应至少硬编码几个已确认的文件名，请给出确认清单（我手上只有 `fruit_atlas.png` 一个确证命名的产物）。

4. **`.uiscreen` 解析器不存在**，所以界面元素清单来自「文件名 + exe RTTI 类名」的推断，非原版布局。所有推断处已标 `[待验证]` 并列入各文件末尾疑问清单。其中**最可能错的是 ResultsScreen 的 MAX COMBO / FRUIT 两列**（纯假设的原版元素）。

5. **`ResultSummary.maxCombo` / `fruitsSliced` 可能需要 FNPBCore 新增对外值**：现有 `ComboTracker` 只有「当前 combo」、`ScoreSystem` 未见「切中水果计数」（我不能确认其内部字段，故未臆造 API）。若两者不存在，App 层先填 0，UI 不会崩，但结算页会缺两列数据——**需要在后续接线任务卡决定是否给 FNPBCore 加只读聚合属性**。

6. **`project.yml` 我按「未改动」处理**：假设 FNPBUI target 的 `sources` 指向 `Sources/FNPBUI` 目录（XcodeGen 自动包含新增 `Screens/` 子目录）。若 project.yml 里是逐个文件列举，则**必须补 6 个新文件路径**，否则 XcodeGen 生成后这些文件不参与编译。

7. **竖屏与 iPad**：横屏按 `GeometryReader` 断点做了一档适配，竖屏只靠 `minimumScaleFactor` + 纵向堆叠兜底，**未做安全区与分屏（iPad Split View）验证**。原版是横屏 only，`Info.plist` 已改 Landscape 双方向（D-T020），若最终锁定横屏 only，这些竖屏分支可以删掉。

8. **编译验证缺口**：本机 Windows，`xcodebuild`/`xcodegen` 全部未跑。代码按 iOS 26 SDK + Swift 6 语言模式书写（依赖 `View` 协议已是 `@MainActor`、`tracking` iOS 16+、`foregroundStyle` iOS 15+、`switch` 表达式 Swift 5.9+），但**零编译证据**，请在 `pipeline/` 的 macOS runner 上做第一次构建后再判定本卡完成。
