### 1.2 vtable 分发（碰撞层入口契约）

```c
int   t    = (**(code**)(**(int**)(param_2 + 0x38) + 0x08))();            // shape->getType()
bool  hit0 = (**(code**)(**(int**)(param_1 + 0x38) + 0x0C))(
                 *(int**)(param_1 + 0x38),      // slash 形状（this）
                 *(int**)(param_2 + 0x38),      // 实体形状
                 &local_3c);                    // out: 交点 vec3
```

- `vtable+0x08`：无参 → int。**`== 1` 即球体**，进入二次确认分支；其余值（0/2/3…）直接返回 `hit0`。
- `vtable+0x0C`：`(otherShape, outVec3) → bool`。这是引擎的**通用形状-形状相交**（对应旧笔记里猜的
  `coline/colsphere/triclipper` 家族由这一槽位多态分发，不需要在调用点区分）。

### 1.3 二次确认（仅球体）

记：
- `c_g = *(vec3*)(slashShape + 0x04)`（+4/+8/+0xC，xyz）
- `c_e = *(vec3*)(sphereShape + 0x04)`
- `r   = *(float*)(sphereShape + 0x14)`（**+0x14 = 球半径**）
- `pt  = local_3c/38/34`（引擎输出的交点，相对量）
- `R² = *(float*)(game + 0xf0)`

控制流（H，逐分支可读）：

```
① d² = |c_g − c_e|²
   if (d² < r²)  →  return TRUE            // slash 参考点落在球内，直接命中（跳过一切）
   否则继续                                 // ★ 注意：这是 if(!(d²<r²)) 包裹的长分支

② if (|pt|² < r²) {                         // 交点落在球内 → 计算截面极值偏移
       k   = sqrtf(r² − |pt|²)               // ← FUN_00301044，球在该点的截面圆半径
       n   = normalize( 由 pt/c_e 构造的切向 )  // ← FUN_00009b50，[待验证] 具体构造式
       off = n * k
   } else {
       off = (DAT_0052bfe0, DAT_0052bfe4, DAT_0052bfe8)   // 推测为零向量 [待验证]
   }

③ p⁺ = c_e + pt + off
   if (|c_g − p⁺|² < R²) → return TRUE

④ p⁻ = c_e + pt − off                      // 关于截面圆对称的另一极值
   if (|c_g − p⁻|² < R²) → return TRUE

⑤ return FALSE
```

> 语义解释：球体与「有粗细的 slash 线段（胶囊）」求交。引擎 `intersect` 只给出球面上一点，作者再沿
> 球面截面圆取 **± 两个极值点**，检查它们是否落进 slash 的切割半径 `R`（`R² = game+0xf0`）内。

## §4 切割判定完整公式（可直接落代码）

```c
// game+0xf0 = R²（切割半径平方）；shape+0x14 = 球半径；1.5f = 近失放大
bool SlashHitTest(Game* g, Entity* e) {
    if (!g->collisionCtx) return false;
    if (!(g->hitRadius2 > 0.f)) return false;
    if (!e || !e->shape) return false;
    if (g->globals->flag18 || g->globals->flag0A) return false;

    int  type = e->shape->vt->getType();                 // vt+0x08
    bool hit0 = g->collisionCtx->vt->intersect(          // vt+0x0C
                    g->collisionCtx, e->shape, &pt);
    if (type != 1) return hit0;                          // 非球：引擎结果即最终
    if (!hit0)     return false;
    return SphereConfirm(g, e->shape, pt, 1.0f);         // 见下
}

// 近失：同一确认函数，半径放大 1.5
bool SlashNearMiss(Game* g, Entity* e) {
    ...同样门控...
    bool hit0 = TempSphereIntersect(e->shape, e->shape->radius * 1.5f, &pt);
    if (!hit0) return false;
    return SphereConfirm(g, e->shape, pt, 1.5f);
}

bool SphereConfirm(Game* g, Shape* s, Vec3 pt, float scale) {
    Vec3  cg = g->collisionCtx->center;      // +0x04
    Vec3  ce = s->center;                    // +0x04
    float r  = s->radius * scale;            // +0x14
    if (dist2(cg, ce) < r*r) return true;    // ① 参考点在球内
    Vec3 off = {0,0,0};                      // = DAT_0052bfe0/e4/e8 [待验证]
    if (len2(pt) < r*r) {                    // ② 截面极值偏移
        float k = sqrtf(r*r - len2(pt));
        off = normalize(perpDir(ce, pt)) * k;
    }
    return dist2(cg, ce + pt + off) < g->hitRadius2   // ③
        || dist2(cg, ce + pt - off) < g->hitRadius2;  // ④
}
```

> `perpDir()` 的构造式在反编译里被 SIMD 失真遮蔽（`FloatVectorMult(...,0,...)`），标 **[待验证]**；

## §3 读取失败诊断（关键：这些不是真值，是管线缺陷）

### 3.1 exe 侧：3 个可疑读数全是「地址推断错误」

| 地址 | 读出 | 应有值 | 判定 |
|---|---|---|---|
| `0x197F47C` | 0.0 | 「上一帧 dt 初值」= 0.0 恰好**正确** | ✅ 真值（语义订正，非失败） |
| `0x16F2028` | 0.0 | 15.0 (0x41700000) | ❌ 推断错 |
| `0x16F2018` | 0xA0000000 | 0.05 (0x3D4CCCCD) | ❌ 推断错 |

**根因假设（按优先级）：**

1. **VA / file-offset 混淆**：exe 是 PE，Ghidra `ram:` 地址是 **VA**，脚本若按文件偏移读会落到别处。
   `0x16F2018` 落在 exe 的 `.rdata` 附近（VA 0x16F0000 区），若按 RVA 读则错位 0x4000（PE headers）。
2. **`_DAT_` 前缀符号在 Debug 版可能是「重叠符号」**：Ghidra 对 PE 的 `_DAT_xxxx` 常把相邻不同宽度
   的字面量合并显示。`core_logic_notes` 里这些地址全部由「函数体引用反查」得来，属**推断地址**，
   未做段校验。
3. 0xA0000000 恰是 `-0.0f` 的高字节模式，说明读到了某个 8 字节 double 的一半 —— 进一步指向 **字节错位**。

**验证方法（5 分钟）：** 用 `objdump -h FruitNinjaPIB.exe` 打印各段 VA/VMA 范围，确认上述 3 个地址
是否真的落在 `.rdata`；再在 `.rdata` 全段扫 float，按候选值反查地址（见 §4）。

### 3.2 macho 侧：`DAT_005d4d74` 页不可读

- 报错 `Unable to read bytes at ram:005d4d74` ⇒ 该 VA 不在任何可读 `__DATA`/`__const` 段内，
  极可能落在 **`__bss`（未初始化段，文件里不占空间）** 或 64KB 段对齐空洞。
- **这不是"没有这个变量"**：主循环 `FUN_00016214` 确实读了 `DAT_005d4d74` 的 `0x40/0x2/0x1/0x10` 位。
  bss 语义 ⇒ **值在启动时为 0，运行期被写入** ⇒ 位掩码是「运行时调试/特效开关」，不是编译期常量。
- ⇒ **该项应判定为「不需要闭合的编译期常量」**，改为「列出位语义」即可：
  从调用点反推（`0x01` 拉近 / `0x02` 推离 / `0x10` 炸弹不可切 / `0x40` 冻结门控）。

### 3.3 macho 侧：`PTR_DAT_004d9048` 指向 `0x00412454`（__TEXT）

- `0x412454` 在代码段 ⇒ 这是 **PIC 的 GOT/lazy-binding stub**，静态读其 `+0x44` 必然得到指令字节。
- 因此「固定步长」用静态数据段读取**原理上就读不到**，必须走运行时或符号解析。

## Kimi 审查时应注意的风险点

1. **验收标准未达成，属任务卡输入缺陷而非执行偏差。** §7 清单 14 项里只有 5 项能闭合；原因是 exe 侧 3 个地址的读数物理上不可能（0.0 / 0xA0000000），是**地址推断错误**，继续读同一地址不会有新结果。建议下一卡先做「段扫描校准」，而不是再猜地址。

2. **`FUN_00017d74` 的向量分量存在系统性失真。** armv7 VFP 单精度被 Ghidra 建模为 `CONCAT44(extraout_sX, …)`，我在 §4 给出的 `perpDir()` 是骨架级还原，**逐分量不可直接照抄**。公式的**控制流与常量（1.5 / R² / r）是 H 置信**，但 `off` 的三轴符号必须动态验证。若直接用这份骨架重写 C++，行为可能有细微偏差（表现为切割手感偏紧或偏松）。

3. **「固定步长」语义反转需升级为 DECISIONS 条目。** 我判定它是「上一帧 dt 缓存」而非 1/60 常量，证据是 exe 静态值 0.0 且门控为 `dt == 0` 才替换。若 Kimi 认可，§1.1 常量表该项应从「常量表」移到「状态字段表」，否则重建时会误写成硬编码 1/60，导致暂停/首帧行为不同。

4. **命中率 K = −0.2 是语义反转，不是小修正。** 原笔记按「K 为正的加成」建模，实际是「每次未得分 slash 扣 20%」。若按原假设实现，命中率会随失误**上升**，是完全错误的结算。这条建议立即进 DECISIONS。

5. **轨迹时长 0.05 s 与 ProMotion 冲突。** 0.05s 在 60Hz 下约 3 帧、120Hz 下约 6 帧。Phase 3 要求 120Hz 时，若按帧数实现轨迹环形缓冲会**改变切割手感**（更长更易切中）。必须用**时间**驱动轨迹存活，而非帧计数——这是现代化改造里最容易漏掉的隐性手感偏差，建议在 PLAN Phase 3 里显式列出。

6. **`FUN_002ed344` 与 `ctx->vtbl+0x0C` 可能同体。** 我在函数地图里给了两个条目，但若确认同体，碰撞层地图应合并——这会影响「碰撞层边界」的定义（是 1 个类还是 2 个）。属低风险但会影响架构图准确性。

7. **`DAT_005d4d74` 判为 bss 是我基于报错文案的推断 [待验证]。** 若实际是段对齐空洞而非 bss，则该变量可能确实有静态初值（意味某些特效开关默认开启），会影响默认行为。建议用 `otool -l` 确认段边界后再定论。

8. **exe 虚表 +0x24 对齐关系仍是悬案。** §1.4 已裁决「exe 虚表比 macho 多一条，重建按 macho 的 +0x24」，本轮 `FUN_00bda510` 片段又出现 `(*piVar4 + 0x24)` 的调用（作用于单例而非 Fruit）。两者不矛盾，但**不能用它反证 Fruit 的槽位**。P-1 未闭合前，OnSliced 的映射关系不宜写进重建代码。
