# FruitInfo 默认值、覆盖顺序与正式 Challenge 新局 `P` 核实

## 0. 结论

- FruitInfo 构造后：`+0x308 = 0`、`+0x318 = 1`、`+0x328 = 0`。
- `FUN_0001267c` 在读取 `chance` 前再次把 `+0x308` 清零；整数属性读取器找不到属性时不会写目标。因此，当前配置中缺失 `chance` 的 `black_pineapple`、`apple_center`、`skynet`，有效 `+0x308` 都是 **0**，不是惯例补值。
- `+0x328` 先继承 `coins`，再被 `coinsMax` 覆盖。当前 24 个 FruitInfo 全部未写 `coins`、`coinsMin`、`coinsMax`，所以当前有效 `+0x328` 全部为 **0**；这不是“缺失 `coinsMax` 永远等于 0”的通用规则。
- 当前配置下，只有 `banana` 的最终 `+0x318 = 0`，原因是果汁颜色 alpha 为 0；其余 23 个水果最终均为 1。三个点名水果的 `+0x318` 都是 **1**。
- 正式 Challenge 新局的官方更新/生成路径中，`P = FUN_0005809c(FUN_00052f80(), 0)` 返回 **0**。决定状态为 `G[+0x70] = 1.0`、波次修正因子 `F = 1.0`、`critical.chance = 50`，故 `1.0 * 1.0 > float(50 / 2)` 为假。
- 现有 Mach-O 函数不接受 `P` 参数；新的值语义选择器可以显式注入 `P`，但官方当前新局默认应注入 0，并保留 `P == 1` 的原始分支判断。

## 1. 范围与证据

目标是 ARMv7 Mach-O `FruitNinjaPuss`。所有 Ghidra 调用均使用 `-readOnly -noanalysis`；未修改生产代码、Mach-O 或工程代码。

核心证据文件：

- `fruit_info_defaults_parser_asm_macho.txt`：`FUN_00015404`、`FUN_0001267c`、`FUN_0005809c`、`FUN_00052fe4` 完整汇编。
- `fruit_info_attribute_reader_asm_macho.txt`：`FUN_0030c6c0`、`FUN_0030c660` 完整汇编。
- `challenge_ac24_predicate_decompile_macho.md`：谓词、全局构造和 Challenge 调用链反编译。
- `challenge_predicate_state_init_asm_macho.txt`：正式更新、波次构造及状态初始化汇编。
- `challenge_state_paths_asm_macho.txt`：`FUN_00061128` 等 Challenge 路径汇编。
- `fruit_weighted_selection_ac24_complete_macho.md` 与 `fruit_weighted_selection_ac24_asm_macho.txt`：已闭合的选择算法及 `P` 消费方式。

配置不是凭 JSON 文件名猜测：本轮直接把 `assets_raw/xml/fruitList.xml` 的 8278 字节 BXML 解码，并逐项比较 24 个 FruitInfo 的属性字典及 `critical` 属性，均与 `Content/fruitList.json` 完全一致。

- 原始 BXML 长度：8278 字节，与 JSON 声明一致。
- 原始 BXML SHA-256：`c7be5c702c8f481496f03a8ddf28d062e2882eb869588d82c553863cd52470ac`。
- 原始根节点：`fruitInfoFile`，`version = 1.0.0`。
- 因而下表是基于原始 BXML 属性核实的配置镜像值，不是按水果类别补出的经验值。

## 2. 构造默认值与解析覆盖顺序

### 2.1 `FUN_00015404` 构造默认值

| 字段 | 构造值 | 汇编证据 |
|---|---:|---|
| `+0x308` | 0 | `0x00015466` |
| `+0x30c` | 0 | `0x0001546a` |
| `+0x310` | 0 | `0x0001546e` |
| `+0x314` | 1 | `0x00015462` |
| `+0x318` | 1（字节） | `0x00015492` |
| `+0x324` | 0 | `0x0001545a` |
| `+0x328` | 0 | `0x0001545e` |
| `+0x330` | 0（字节） | `0x0001543e` |

`+0x30c/+0x310` 随后还会被 `FUN_0000ac24` 用作累计权重缓存；它们不是 XML 中的水果权重默认值。

### 2.2 `FUN_0001267c` 的准确顺序

1. 颜色 alpha 为 0 时，`0x00012dc4..0x00012dca` 把 `+0x318` 清零。
2. `0x00012e40` 再把 `+0x308` 整体清零；`0x00012ecc..0x00012ed2` 读取 `chance` 到 `+0x308`。
3. `0x00012ed6..0x00012ee6` 读取 `score` 到 `+0x314`；若结果为 0，`0x00012eea..0x00012ef8` 把 `+0x330` 置 1。
4. `0x00012efc..0x00012f0a` 读取 `coins` 到 `+0x324`。
5. `0x00012f0e..0x00012f14` 执行 `+0x328 = +0x324`。
6. `0x00012f18..0x00012f24` 读取 `coinsMin` 到 `+0x324`。
7. `0x00012f28..0x00012f38` 读取 `coinsMax` 到 `+0x328`。
8. `0x00012f66..0x00012f72` 若 `DAT_0052bf64 <= info[+0x314]`，把 `+0x318` 清零。当前 `DAT_0052bf64` 来自全局 `critical.score = 10`。
9. `0x0001302a..0x00013078` 最后处理 `noCritical`：非空时写入 `strcmp(value, "true") != 0`；缺失或空字符串时，只把现有 `+0x318` 规范化为 0/1，不会把已清零值恢复为 1。

因此：

- 缺失 `coinsMax` 时，`+0x328 = coins`（若 `coins` 也缺失，才继承构造值 0）。
- `coinsMin` 不再影响 `+0x328`。
- `+0x318` 不是原始 `noCritical` 文本布尔值，而是颜色、score 阈值和 `noCritical` 依次覆盖后的最终字节。

### 2.3 缺失整数属性的行为

`FUN_0030c6c0` 在 `0x0030c6d4..0x0030c6da` 找不到属性时直接返回 1，不调用 `_sscanf`，也不写 `param_3`。只有找到属性后才在 `0x0030c6f2..0x0030c702` 尝试解析并写目标。

这闭合了“缺失字段保留调用前值”的规则；当前配置中的有效缺省值均可由构造值和上述覆盖顺序直接得出。

## 4. 正式 Challenge 新局的 `P`

### 4.1 精确公式

令 `G = FUN_00052f80()`，即全局对象 `0x005a7b80`；索引参数为 0：

```text
M = float(G[+0x70])
F = (G[+0x168] != NULL) ? float(G[+0x168][+0xa4]) : 1.0
C = int32(DAT_0052bf68)       // fruitList 的全局 critical.chance
T = float(C / 2)              // 有符号整数除法，向零截断
P = (M * F > T) ? 1 : 0
```

汇编依据：

- `0x000580a0..0x000580ac`：默认 `F = 1.0`，指针非空时读 `+0xa4`。
- `0x000580b8`：读取 `G[+0x70]`。
- `0x000580be`：执行乘法。
- `0x000580c2..0x000580d2`：读取 `DAT_0052bf68`，计算向零截断的半值并转浮点。
- `0x000580d6..0x000580e0`：只在乘积严格大于半值时返回 1。

### 4.2 新局决定状态与返回值

1. `FUN_0001267c` 在 `0x00012850..0x00012866` 把全局 `critical.chance` 读入 `DAT_0052bf68`；原始 BXML 为 50，所以 `T = 25.0`。
2. 正式主更新 `FUN_0001f018` 的两条路径都调用 `FUN_000559e4(G, ...)`。其活动分支在 `0x00055a36..0x00055a46` 把 `G[+0x70]` 写为 `0x3f800000`，即 `M = 1.0`，随后才进入生成更新 `FUN_000557ac`。
3. 若当前波次指针为空，谓词自身使用 `F = 1.0`。若非空，波次对象 `FUN_00058ee4` 在 `0x00058f34` 默认写 `+0xa4 = 1.0`，并在 `0x00058f88..0x00058f8a` 从全局波次默认 `G[+0xb8]` 复制；`FUN_00052fe4` 把该默认值初始化为 1.0。当前 `originalWaveList` 的唯一 `criticalChance` 也是默认值 1.0，Challenge 配置未给出另一个 `criticalChance`，所以新局 `F = 1.0`。
4. 代入：`P = (1.0 * 1.0 > 25.0) = 0`。

所以正式 Challenge 包装函数以 `param_1 = 0` 调用 `FUN_0000ac24` 时，新局走的是 **`P != 1 && param_1 == 0` 的 `T_free` 路径**，筛选条件仅为 `+0x328 <= 0`；不是 `T_flagFree` 路径。

### 4.3 状态边界

`FUN_00052fe4` 本身没有初始化 `G[+0x70]`，因此不能只凭构造函数宣称 `P` 是进程 lifetime 内的常数。这里的 `P = 0` 限定为已核实的正式更新/正式 Challenge 新局生成路径及当前原始配置；外部修改器、存档异常或尚未经过正式更新的瞬时内存状态不在此结论内。

## 5. 值语义选择器能否显式注入 `P`

可以，但分为两个层面：

- **现有 Mach-O 接口**：不能直接传入 `P`。`FUN_0000ac24` 内部固定调用 `FUN_0005809c(FUN_00052f80(), 0)`，只能由全局状态间接决定。
- **新的值语义实现**：可以把 `p` 作为显式输入，与候选 ID、各 FruitInfo 有效字段、四个累计状态和 PRNG 状态一起传入。分支必须保持 `p == 1`，不要把任意非零值都当成真。

建议把“官方状态求值”和“选择算法”分开：

```text
officialP = evaluatePredicate(globalState, criticalChance)  // 当前正式新局 = 0
result    = selectWeighted(..., p: officialP)
```

测试也可以注入 `p = 0` 和 `p = 1` 覆盖两条路径，但这些测试输入不能冒充官方新局状态。当前官方 Challenge 新局默认应使用 `p = 0`。

## 6. 仍不明确或未外推的字段

- 对当前 24 个原始 FruitInfo，本任务要求的 `chance/+0x308`、最终 `+0x318`、`coinsMax/+0x328` 均已明确，没有需要按惯例补值的条目。
- 非数字或部分数字属性的 `_sscanf` 边界不影响当前配置，未据此扩展结论。
- `G[+0x70]` 在对象刚构造、尚未进入正式更新时的瞬时值未闭合；不能用该瞬时状态替代正式新局结果。
- 外部修改、非官方存档或其它资源配置可能改变 `M/F/C`；这些情况应重新求值，不应硬编码为永久 `P = 0`。
- 本结论只证明字段值与选择分支，不改动也不验证任何 Swift 重建实现。
